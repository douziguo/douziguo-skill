# 同步纪律（先同步、后给码）

## 为什么这是最高优先级

助手读到的往往是用户侧权威源码的一份镜像/快照（典型如只读挂载目录、导出副本）。如果基于过期快照给改动：
- 函数行号对不上，用户无法按要求替换；
- 给出的是"已被用户改掉/回退"的旧函数，改完反而覆盖掉正确版本；
- 反复返工会让用户强烈不满。

因此：**任何读码或给码之前，镜像必须是本轮同步过的最新版**。

## 触发时机

- 用户报新问题、要给新函数、要复查行号——一律先同步。
- 用户贴过代码、手工改过文件、编译部署过之后——镜像即视为过期，下一轮必须重新同步，哪怕上一轮刚同步过。
- 自检口令：给码那一刻问"这份内容是用户当前最新版吗？本轮读过同步后的副本吗？"答不上来就先要同步。

## 判断同步范围

- 依据"本轮方案会不会改/读这个文件"，不是"先读它才知道要不要"。
- 拿不准按"要改"算，宁可多同步一个。
- 禁止用"先定位文件才能把同步范围缩到最小"当借口先读旧快照。
- 默认只同步本轮真正要改/要读的关键文件；全量同步仅在首次建基线或大范围重构时用，且先说明原因。

## 定位粒度

- 定位阶段只允许粗粒度手段：目录列表、文件名级 grep（只返回文件名、不返回行号与内容）、截图。
- 一旦要输出行号、或断言"某函数在某文件第几行"，必须已经同步并读过最新副本。
- 同步完成前，不要说"冲突点在哪一行""这个文件里有什么"。

## 同步指令写法

- 单条、单行、可直接粘贴执行；无变量、无反斜杠续行。
- 需要多步时用 `;` 串成一行。
- 末尾带 `md5sum` / `stat` 校验，让用户能确认同步确实成功。
- 多文件用单文件 cp 链，例如：

```bash
cp <权威>/A.cpp <镜像>/A.cpp ; cp <权威>/A.h <镜像>/A.h ; md5sum <镜像>/A.cpp <镜像>/A.h
```

## 只读镜像纪律

- 镜像/挂载目录绝不写入或编辑，只用于读取；所有改动只在对话里给出，由用户手工落到权威源码。
- 曾在用户执行同步的同时写镜像，导致并发写冲突、副本视图撕裂（读到全零垃圾、新旧内容混杂、元数据与内容不符）。遵守只读即可根除。

## 复原方式

- 镜像通常没有版本控制，不能用 `checkout` 回滚。
- 给出本轮改动时，同时给上一轮改动的复原方式：回贴原函数体 + 列出要删除的新增成员。
- 镜像里往往就是改动前的原貌，可当作复原基准，但要逐个核对头文件里有没有新增成员来确认。

## 典型失误案例（引以为戒）

- 用户贴了某文件代码后，未重新同步就基于旧副本继续给新函数 → 行号与内容全错。
- 以"缩小同步范围"为由先读旧快照，再顺着旧快照推演方案、报行号 → 污染用户判断。
- 想当然认为"这文件最近没动过"就跳过同步 → 违反最高优先级。

## 生成中间文件过期的编译报错

若出现"源码里有控件/符号，编译却报未声明"，可能是构建缓存里的生成头文件（如 UI 编译器产物）过期。先清理对应生成文件、触碰源文件触发重新生成、再 qmake/重编。给出此类命令前仍需确认真实文件名（先列目录，不猜大小写）。
