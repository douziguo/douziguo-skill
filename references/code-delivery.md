# 交付规范（怎么把改动交到用户手里）

## 给完整函数，不给片段

- 改动落在函数里 → 整段重贴该函数，从签名到收尾大括号。
- 禁止"第 N-M 行替换成…""在某行后插入"这类片段式改法。
- lambda、闭包、内层代码块里的改动 —— 同样重贴其**外层完整成员函数**，不能只贴 lambda 段。
- 同一目标要改多个函数 → 每个都给完整版，不遗漏。
- 原因：片段式改法要求用户自己拼装，行号稍有偏差就改错；且用户明确反感这种偷懒。

## 少改头文件

- 现场编译耗时长，改头文件会触发全量重编。
- 优先把新增逻辑放进 .cpp 内部：匿名 namespace 里的辅助类、lambda、局部结构体，用回调与宿主通信。
- 实在要改头文件，先说明理由。
- 改动只涉及 .cpp 时，提醒用户增量编译即可，不必全量清理重建。

## 一次一个目标

- 一次只推进一个改动目标，改完等用户确认再给下一个。
- 每步都要能独立编译；若有止血项（崩溃、起不来），排最前面。
- 不要一股脑抛出多个目标的改动让用户一次性贴。

## 不擅自改 UI/界面描述文件

- 优先用代码在运行时覆盖布局与文案：设置文本、间距、边距、样式表等。
- 除非用户明确同意，不动界面描述文件本身。

## 不生成 md 交付文件

- 代码直接贴在对话里，由用户手工修改。
- 不额外生成 .md 或其他文档文件当作交付物。

## 给码的标准格式

1. 先讲根因与方案（设计变更/多方案时先让用户拍板，不急着给码）。
2. 完整函数代码（必要的头文件改动单独列出并说明理由）。
3. 简短说明：改了什么、有哪些可调参数、注意事项。
4. 末尾提醒：改完贴回权威源码后，下一轮需重新同步（镜像已过期）。
5. 若覆盖了上一版改动，附复原方式。

## 沟通分寸

- 用户说"先理清思路、先不修改代码"时，只给分析/方案，不给代码，末尾问"是否开始改"。
- 有多个决策点时，用选择题让用户拍板（例如：失败时阻断还是放行、改在哪一层、是否保留旧机制），把选项和后果列清楚。
- 方向由用户定：用户指明的修改层次就是目标层，不许下钻到更下层"顺手"打补丁。
